# MachineContext 产品方向

## 1. 定位

MachineContext 是一个私有、可验证、AI 可快速读取的本机上下文层。它把“这台电脑现在是什么状态”整理为稳定、轻量、可维护的事实，让网页端 ChatGPT、本地 Codex/Agy 以及未来其他 Agent 在规划软件安装、开发环境、项目工作、更新迁移和排障时，不必反复向用户询问版本、路径、已有工具和环境关系。

它首先是一个 **文件仓库 + 本地维护工具**，而不是传统桌面软件。

## 2. 核心问题

目前网页 AI 无法直接看到本机，因此经常出现额外往返：先给方案 -> 用户本地查版本/路径/依赖 -> 再反馈 -> AI 重做方案。聊天记忆也可能陈旧，且无法作为机器当前状态的可靠来源。

MachineContext 要消除这部分摩擦，并提供跨会话、跨 Agent 的统一机器事实。

## 3. 产品原则

项目最重要的属性是：

1. **可维护**：信息必须容易重新检测、验证和更新，不能依赖长期手工记忆。
2. **便捷迅速**：AI 通常先读一个短入口，需要时再按模块深入。
3. **完整详细**：保留足以支持安装、开发、迁移和排障决策的事实及关系。
4. **实时可信**：易变化的信息应带验证状态和时间，旧记录不能伪装成当前事实。
5. **轻便简洁**：不做完整资产管理，不复制已有项目 manifest，不积累无意义原始扫描数据。
6. **可扩展**：未来增加新的软件类别、项目、多台机器或更好的交互方式时，应主要通过新增模块完成，而不是推翻目录和数据模型。

## 4. V1 用户体验

对网页端或本地 AI：

`CURRENT.md -> machine-context.yaml -> 按需读取 context/*`

对本机维护：

`scan -> verify -> privacy check -> update canonical context -> render CURRENT.md -> review diff -> commit/push`

理想情况下，用户不需要记住大量维护步骤。后续可收敛为一个类似 `mc sync` 的入口。

## 5. V1 范围

第一阶段优先覆盖：

- Windows、硬件、磁盘、Shell、关键 PATH 与目录；
- 开发 runtime、包管理器、SDK、编译器、CLI 和开发工具；
- AI coding / harness / bridge 工具；
- 与开发决策相关的网络、代理、本地服务与端口；
- 本机长期开发项目及其环境级依赖；
- 软件安装位置、安装方式、更新方式和目录使用习惯；
- 对规划和排障有价值的跨工具/项目关系；
- 隐私安全、验证状态和过期检测。

## 6. 明确不做

V1 不做：

- 完整 Windows 软件资产管理；
- 所有进程、端口、注册表或文件的原始 dump；
- secrets/凭据管理；
- 复制项目 lockfile 或完整依赖树；
- 为了“像产品”而提前引入数据库、服务端或复杂 GUI；
- 自动修改系统环境以迎合清单。

## 7. 后续设想

以下方向保留，但只有在真实使用证明有价值后才实现：

- **非开发软件上下文**：浏览器、设计/创意、生产力、媒体、常用工具等，以新的 software module 加入；
- **轻量 CLI**：如 `mc scan`、`mc status`、`mc sync`、`mc project add`；
- **更好的变化检测**：只更新发生变化的事实，并提示影响关系；
- **安装建议辅助**：基于实际磁盘用途、既有目录规范、更新方式和下游依赖，辅助判断软件应该装在哪里、如何安装和如何更新；
- **多机器支持**：如果未来出现第二台长期使用设备，再在不破坏单机体验的前提下增加 machine identity/profile；
- **本地 Dashboard**：只有当文本/CLI 已无法满足浏览和维护效率时再考虑。

这些方向都不得破坏一个原则：即使未来增加 UI 或 CLI，仓库中的可读结构化文件仍应保持为可迁移、可审计的核心数据层。
